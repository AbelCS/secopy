# XXH128 for every hash — design

Approved in conversation on 2026-10-03. Replaces xxHash64 (RFD §4, FR-20, FR-29, FR-30, FR-34,
FR-46, FR-52, FR-57).

## Goal

XXH128 is Secopy's one hash: every checksum Secopy computes, writes, reads or compares is
XXH128. Secopy is in beta, so nothing written by earlier versions has to be read: old `.xxh64`
files, mirror checksum files and ASC MHL hashes need no compatibility.

Success: every copy, read-back, Verify, mirror comparison, checksum file, report and ASC MHL
history uses XXH128; `xxhsum -c` checks Secopy's checksum files; the ASC reference tool verifies
its histories; nothing is slower.

## First priority: never lose or corrupt data

This change touches how Secopy proves a copy is good. These rules come before everything else:

- **One type, no mixing.** Hashes are a `Hash` type (128 bits), not bare integers. Code that
  still expects 64 bits doesn't compile, so a hash is never cut short, padded or compared with
  a hash of another width.
- **Streaming equals one-shot.** The copy hashes chunk by chunk, the read-back with other chunk
  sizes. For every size XXH128 handles differently (0, 1–3, 4–8, 9–16, 17–128, 129–240, more than
  240 bytes, across buffer boundaries), hashing in any split gives the same value as hashing the
  whole. A mismatch here would make good copies fail, or let a bad one pass.
- **The same values as `xxhsum`.** Reference values, and generated files of many sizes, are
  checked against `xxhsum -H2` (the device test runs `xxhsum -c` on a real checksum file).
- **Strict reading.** A checksum line is 32 hex characters, two spaces, a path. Anything else
  (including an old 16-character xxh64 line) is a problem said for that line, never read as a
  hash, never zero-extended.
- **Nothing written differently.** What is copied, overwritten, verified, archived or undone
  doesn't change; only the hash does. Overwrite still replaces a file only after the new copy is
  complete (and verified in Copy & Verify).
- **Old files are left alone or handled by the normal rules.** An old `.xxh64` checksum file
  in a copy's destination is an ordinary file: Secopy never removes it. An old mirror checksum
  file (`.secopy-checksums.xxh64`, or one set aside as `….damaged-…`) is no longer Secopy's own
  file, so the next mirror run handles it like any file the origin doesn't have: listed in the
  preview, then archived (or deleted, in a Delete mirror). An old unfinished file
  (`.secopy-<16 hex>.partial`) is still Secopy's own file (never copied, mirrored or removed);
  it just isn't recognised as a leftover of the file it belonged to, so it stays, hidden.
- **A failed hash library is never silent.** If the speed check fails, we change the library;
  we never fall back to xxh64 quietly.

## What changes

| Where | Before | After |
|---|---|---|
| Hash | xxHash64, seed 0, 16 hex | XXH128 (XXH3 128-bit), seed 0, 32 lowercase hex, as `xxhsum -H2` prints |
| Copy, read-back, Verify | xxh64 | XXH128 |
| Mirror Paranoid | xxh64 of both sides | XXH128 of both sides |
| Copy checksum file | `secopy_<date>.xxh64` | `secopy_<date>.xxh128`, same line format |
| Mirror checksum file | `.secopy-checksums.xxh64` | `.secopy-checksums.xxh128` |
| Verify | reads `.xxh64` | reads `.xxh128` only |
| Unfinished files | `.secopy-<16 hex>.partial` | `.secopy-<32 hex>.partial` |
| ASC MHL | `<xxh64>` | `<xxh128>` |
| Report | field `xxh64` | field `xxh128` |
| Secopy's own files (never copied or mirrored) | `.xxh64` names | `.xxh128` names |

## ASC MHL

A new history records `<xxh128>`. A continued history compares each file with its earlier
XXH128 (`verified` or `failed`, as now). A file an earlier generation recorded only in another
format (xxh64, md5, sha1, c4) gets its XXH128 as `original`: not verified, never failed, and
never a reason to refuse the copy. This is how Secopy already treats md5, sha1 and c4.

## App, CLI and words

- The finished list's Checksum column shows all 32 characters; the column widens, and long file
  names truncate as they do now.
- Settings › Write the checksum file: the help shows `secopy_….xxh128` and `xxhsum -c`.
- `errors.check.notAChecksum`: "“{hex}” isn't an XXH128 checksum" (English and Spanish).
- The CLI writes and checks `.xxh128`; its help and output say XXH128.
- Docs: RFD (§4 glossary, FRs above, decision log), user guide, README, `docs/i18n.md` terms
  (checksum = the XXH128 of a file's contents).

## Library and speed

**`twox-hash` 2.1.4** (MIT; default features off, `xxhash3_128` and `std` on) replaces
`xxhash-rust`, so Secopy keeps one hash library. Measured on an M2 Max (one core, release
build, data in memory, 4 MiB chunks as Secopy reads them), chosen 2026-10-03:

| Library | Streaming (large files) | One go (4 KiB–1 MiB) |
|---|---|---|
| xxh64, `xxhash-rust` (before) | 15.6 GB/s | 15.0–15.7 GB/s |
| XXH128, `xxhash-rust` | 26.8 GB/s | 37.4–38.6 GB/s |
| **XXH128, `twox-hash`** | **39.9 GB/s** | **38.9–40.1 GB/s** |
| XXH128, official C (`xxhash-c-sys`) | 17.1 GB/s | — |
| `xxhsum` (C tool) | 41 GB/s | |

All three gave identical values, the same as `xxhsum -H2` ("abc" and a 256 MiB random file).
A benchmark kept in the repo (an ignored test, run by hand on a release build, never in CI where timing is noisy) checks streaming XXH128 is at least 15.6 GB/s here.

## Tests

- Hash: reference values against `xxhsum -H2`; streaming in random splits equals one-shot, for
  every size class above; hex is 32 lowercase characters.
- Checksum file: written and parsed with 32 hex; a 16-hex line is a problem; `xxhsum -c` passes
  (device test).
- Copy & Verify: a corrupted copy still fails, an intact one passes (the existing tests, on
  XXH128).
- Verify: `.xxh128` files read; `.xxh64` files not read ("No checksum files here" when only
  those).
- Mirror: Paranoid finds a same-size, same-date change; the checksum file is `.xxh128`; an old
  `.secopy-checksums.xxh64` in the destination is in the preview as deleted in the origin.
- ASC MHL: `<xxh128>` written; a continued history verifies; a file recorded only as xxh64 is
  `original`; the reference tool's `ascmhl verify` passes.
- Report: `xxh128` field; the text report's column.
- UI: the full hash in the Checksum column; the Settings help.

## Not now

Reading old `.xxh64` files; a choice of hash; a second checksum file (MD5); SHA-256.
