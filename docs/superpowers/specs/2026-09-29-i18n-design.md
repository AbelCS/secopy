# Translation support (i18n) — design

Issue #84. Approved in conversation on 2026-09-29.

## Goal

Secopy is developed in English, but ready for other languages: every text a person sees in
the app comes from a message catalog, so adding a language is translating one file, not
rewriting screens. No language other than English is added now.

Success: the app reads exactly as today in English; no screen has text written directly in its
code (a test says so); every message key Rust can send exists in the catalog; a second language
would be a copy of `en.json`, translated, with a test pointing at anything missing.

## Decisions (from the conversation)

| # | Decision |
|---|---|
| D1 | Translatable: everything the user sees in the app — screens, messages from Rust (errors, reasons, the menu bar panel), native menus, notifications. Job report files and the CLI stay English (records you share or search). |
| D2 | Rust sends codes, not sentences: `Message { key, args }`; the UI turns them into words from its catalog. Rust knows no language. |
| D3 | Catalogs are JSON files, one per language, with a small layer of our own (no i18n dependency). |
| D4 | Language: the Mac's language when a catalog exists for it, English otherwise. No setting until there is a second language. |

## The catalog

- `ui/src/locales/en.json`, nested by screen or area: `copy.*`, `mirror.*`, `verify.*`,
  `queue.*`, `summary.*`, `settings.*`, `presets.*`, `import.*`, `export.*`, `menubar.*`,
  `menu.*` (native menus), `notify.*`, `errors.*` (from Rust), `format.*` (shared bits).
- A value is a string with placeholders, `"There is already a preset called “{name}”."`, or,
  for plurals, an object of forms chosen with `Intl.PluralRules`:
  `{ "one": "{count} file", "other": "{count} files" }`.
- `ui/src/lib/i18n.ts`: `t(key, values?)` returns the text; `values` fill the placeholders
  (numbers through the locale's number format). A missing key is an error in tests and shows the
  key itself in the app (never a blank). The current locale is chosen once at start.
- Types: keys are typed from the JSON import itself (`typeof en`), so a wrong key is a type
  error with no generated file. JSON can't give the texts as literal types, so a missing
  placeholder value is caught at runtime instead: `t()` throws in tests.
- Formatting (`ui/src/lib/format.ts`): numbers, sizes, percentages, durations and dates use
  `Intl` with the current locale instead of the fixed `en-US`. In English the output is
  unchanged (the existing tests pin it).

## Messages from Rust

- `crates/secopy-app/src/message.rs`: `Message { key: &'static str / String, args:
  BTreeMap<String, Arg> }`, `Arg = Text(String) | Number(i64/u64) | Message(Box<Message>)`
  (for "Stopped: {why}"), serialized for the UI as `{ key, args }` and exported to TypeScript
  (specta). Built with a small macro or builder: `msg!("errors.preset.nameTaken", name = n)`.
- Every user-facing string the app sends becomes a `Message`: command errors
  (`Result<T, Message>`), and DTO fields that carry text — `pickProblem`, `blocker`, `reason`,
  `fatal`, `stoppedBecause`, `checksumError`, `reportError`, `problems`, `warnings`,
  `lastError`, `saveError`, the Import screen's changes and problems, the menu bar panel's
  words, and the rest found by the plan's inventory.
- The engine (`secopy-core`) keeps its English `Display` for the CLI and the reports; the app
  maps each engine error (`FileError`, `FatalError`, blockers, pre-flight problems) to a key
  with its details (`errors.file.changed { expected, actual }`, …).
- The UI shows a `Message` with `t(message.key, message.args)` (nested messages first).
- Saved data: `queue.json` stores a job's last error; it becomes a `Message`. An old file's plain
  string still loads, as `errors.legacy { text }` shown as it was (English), until the job
  runs again. Nothing else Secopy saves holds user-facing text.
- A Rust test collects every key the app can send (a registry the `msg!` macro feeds, or a scan
  of the source) and checks each exists in `en.json` with the same placeholders.

## Native menus and the menu bar panel

- The File and View menus' items read their labels from `en.json` (`menu.*`), embedded at build
  time, with the same lookup; macOS's standard items (Quit, Edit, Window…) are already
  localized by the system.
- The menu bar panel is a UI page: its words come from the catalog like any screen; Rust sends
  it figures and `Message`s, not sentences.
- Notifications are built in the UI (`summaryText.ts`) from the catalog.

## Keeping it that way

- A test scans `ui/src/**/*.svelte` (not tests, not the gallery) for text between tags and for
  `label=`, `aria-label=`, `placeholder=`, `title=`, `help=`, `legend=` attribute values written
  directly, and fails on any with letters; symbols ("→", "·", "…", "✓", "✗") are allowed.
- A test fails when a key in `en.json` isn't used anywhere (dead text) and when any other
  catalog lacks a key `en.json` has (for later languages).
- The design system's word rules (directory not folder, presets, short labels) now say the
  words live in `en.json`; AGENTS.md says never to hard-code user-facing text.
- Docs: `docs/i18n.md` — how to add a language (copy `en.json`, translate, run the tests).

## Delivery

Three PRs, each leaving the app identical in English and every test green:

1. **UI:** the catalog, `t()`, locale-aware formatting, the no-hard-coded-text and unused-key
   tests, and every UI text moved into `en.json`.
2. **Rust messages:** `Message`, the key registry test, commands and DTOs sending codes, engine
   errors mapped, `queue.json` compatibility, the UI rendering them.
3. **Native menus, the panel, docs:** menu labels from the catalog, the panel's words, the
   design system and AGENTS.md rules, `docs/i18n.md`.

## Testing

- The existing tests (they check English text) stay green through all three PRs: they are the
  proof nothing changed.
- `t()`: placeholders, plurals (`one`/`other` via `Intl.PluralRules`), nested messages, a
  missing key.
- Formatting in English unchanged; a locale switch in a test changes number formatting.
- Rust: every sendable key exists with matching placeholders; `queue.json` with an old string
  error loads; `Message` serializes as `{ key, args }`.
- The scans: a component with written text fails the test (checked with a fixture).

## Review focus

1. A message that reaches the screen as a raw key or a blank because a key or placeholder is
   missing.
2. A text the scan can't see (built in TypeScript with string concatenation, a `title` set in
   code, `api.confirm` arguments, notification text).
3. Saved queues from older versions still loading.
4. Plurals and number formatting that change the English output.
5. Rust messages whose details (paths, names, counts) are lost on the way to words.

## Out of scope

Any language other than English; a language setting; translating reports or the CLI;
right-to-left layouts.
